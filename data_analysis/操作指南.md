## 以下为各代码文件的详细情况说明
### github_spider.py
#### 采样条件：
- 语言限制：如`language:Python`
- 创建时间的头尾时间限制：如`created:2019-01-01..2019-12-31` 
- star数限制：下限限制（现在的数据版本是只限制了下限，但是发现采到的都是大热项目，建议加上限，或者分桶采样）
- fork限制：限制fork与否，去噪

#### 最大访问数
```
max_accessible = min(total_count, 100)
```   
测试限制的是100条  
由于github限制，只能访问前1000条数据，不能直接获取仓库，所以需要先访问结果，再进行采样

#### 随机采样
```
page = random.randint(1, max_page)
repo = random.choice(items)
```  
随机选page，再在page内随机选仓库
#### 最终的采样数是sample_size，测试是20  

#### 当前问题
1. 采样速度一般般，但也还行，如果要增加采样数量，考虑减少主动的sleep限制

2. 限制条件增加
目前看来只有star数上限的增加 

3. 编写一步到位脚本
现在只能手动换采样，如果采样种类多，考虑写个脚本啥的  

### step1.py
逐个分析仓库，拉取其完整文件树，判断是否存在以下文件：  
- requirements.txt
- pyproject.toml
- setup.py
- environment.yml
- Dockerfile  

然后在根目录寻找readme文件，拉取原文  
然后计算包含 环境/依赖关键词 的行数，关键词写在`README_ENV_KEYWORDS`里了  
计算有多少是环境相关的  

#### 数据来源完整性
| 文件               | 覆盖      | 说明        |
| ---------------- | ------- | --------- |
| requirements.txt | ✅       | Python 主流 |
| pyproject.toml   | ✅       | 现代规范      |
| setup.py         | ✅（仅存在性） | 命令式       |
| environment.yml  | ✅       | Conda     |
| Dockerfile       | ✅       | 系统级       |  
较为完整  

### step2.py
基于静态分析（AST+requirements），不实际克隆、执行或者安装依赖  
#### 对随机抽样到的项目，统计：
- import 出现但 requirements 中不存在的包比例
- requirements 中存在但代码未使用的包比例

#### 数据来源：
- Python 源码 → AST 解析 import
- 依赖声明 → `requirements.txt` / `pyproject.toml`
- 对齐规则 → 映射到 PyPI 包名

#### 存在问题待解决或者答疑：
1. 运行速度极慢（是真的，非常慢的意思）
限制来源于请求量 * 文件量 * AST解析  
部分仓库特别特别慢，例如`Project-MONAI/MONAI`  
但有些又很快  
主要还是前面的仓库可能都属于大项目，导致文件量较大，所以分析速度慢
并且为了保证获取，主动使用了`time.sleep(0.5)`降速  
在保证全读取的情况下，考虑`移除部分主动降速`和`并发读取`  

2. AST读取合理性
- 别名可以被读取
- 子模块的import可能被粗粒度合并，例如：  
| PyPI 包          | import 名 |
| --------------- | -------- |
| scikit-learn    | sklearn  |
| python-dateutil | dateutil |
| pillow          | PIL      |
| beautifulsoup4  | bs4      |
| opencv-python   | cv2      |  
- 本地相对import，会被误判
- 动态import会被忽略，例如`module = __import__("numpy")` 按gpt的说法，比例极低，可以被忽略

因此，对于子模块的问题，可以考虑引入映射表，只修正高频错误，这个可以根据最后的统计结果来二次修正，下面为举例
```
IMPORT_TO_PYPI = {
    "sklearn": "scikit-learn",
    "cv2": "opencv-python",
    "PIL": "pillow",
    "bs4": "beautifulsoup4",
    "dateutil": "python-dateutil",
}
```  

3. 依赖未被完全读取
| 文件               | Step 1 是否统计 | Step 2 是否解析 | 现状                             |
| ---------------- | ----------- | ----------- | ------------------------------ |
| requirements.txt | 已读           | 已读           | OK                             |
| pyproject.toml   | 已读           | 已读           | **仅解析 `project.dependencies`** |
| setup.py         | 已读           | 未读           | **完全忽略**                       |
| Dockerfile       | 已读           | 未读           | **完全忽略**                       |  
所以现在的不一致率是虚高的  

gpt给出的解释是 setup和dockerfile不完全标准
| 文件         | 问题                   |
| ---------- | -------------------- |
| setup.py   | 可执行 Python，依赖可能是动态生成 |
| Dockerfile | 系统级 + Python 混杂，语义复杂 |  
所以目前的统计应该还是可行的


### step3.py  
用 时间差 作为代理指标，衡量仓库的代码演进是否伴随着依赖配置的同步维护  
1. 获取仓库整体最新更新时间
2. 确定现在时间  这个可以改成一个统一的时间节点，目前是实时获取的 
3. 获取依赖文件的最后修改时间
4. 计算两个时间差：
- 相对仓库演进的滞后
- 相对当前时间的滞后

输出的单位是天数  

### step4_issue_env_analysis.py
对已随机抽样的仓库，系统性统计其 Issue 中“环境 / 依赖相关问题”的数量、比例和关键词分布，用以刻画开发者层面的真实需求。  

构造了环境关键词，详见`ENV_KEYWORDS`和`TOOLCHAIN_KEYWORDS`，采取弱NLP＋强规则的模式  

实际关键词统计，需要满足先击中是环境相关的问题，也就是要有`ENV_KEYWORDS`  
然后需要满足环境失败，也即接着击中`TOOLCHAIN_KEYWORDS`  

有设置最大的issue访问数，可以考虑扩大

### step4_onboarding_analysis.py 
1. CONTRIBUTING.md 分析
- 存在性、总行数
- 环境/依赖行数与测试行数
- 环境行占比
按照行进行拆分，统计环境行的数量以及占比

2. 新贡献者 Issue 分析
- author_association == FIRST_TIME_CONTRIBUTOR
- 环境相关 Issue 统计、关键词统计
筛选新贡献者的issue，查看其中有关环境的  
和上一步中的issue统计相比，较为宽松，只要命中了任何关键词就可被统计，可以视为新贡献者对环境感到疑惑吧，上一步中的就是确认的环境不行的比例   

3. 新贡献者 PR 分析
- merged == false → 失败
- PR 标题/描述含环境关键词或改动文件少 → 环境失败
- 输出总数、失败数、环境失败数、比例
筛选新贡献者的pr，判断拉取是否成功，以及失败的原因，其中因为环境失败的占比
